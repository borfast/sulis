VerdictThe bones are good; the seams are where the risk lives

This is a better-than-average auth library. Session and reset tokens are hashed at rest, token consumption is a documented atomic store contract, Argon2id parameters exceed OWASP minimums, login timing is equalized against a dummy hash, TOTP has real replay protection with a monotonic counter, recovery codes are 80-bit and hash-only, and the verified-email session gate defaults to on. The commit history shows deliberate, iterative hardening rather than a feature rush.

The residual risk is concentrated in three places, and none of them is a cryptographic mistake. First, nothing in the library knows whether a user has a second factor, so the happy path silently issues full sessions that skip 2FA entirely — including through magic links. Second, WebAuthn user verification is never enforced, which quietly downgrades a passkey from “something you have plus something you are” to bare possession. Third, the store interfaces delegate correctness to prose: whole-row user updates invite lost-update races, and every consumer hand-writes the SQL that the security properties depend on.

Fix those three and this is a package you can put your name on. The rest of this document is the specifics, in priority order.

Already solidWhat not to change

Worth stating plainly, because a hardening pass shouldn't regress any of it.

  • Hash-at-rest for every bearer secret. Session tokens, reset/magic/2FA/verification tokens, and recovery codes are all SHA-256'd before the store sees them; createSession clears Session.Token on the persisted copy, and ValidateSession looks up by hash.
  • Atomicity as a contract, not a hope. TokenStore.ConsumeToken and recovery.Store.ConsumeCode both require lookup-and-mark in one operation, and totp.Store.SaveTOTP requires a monotonic counter that fails closed.
  • Expiry checked after consumption (sulis.go:396) — failures burn the token, which is the safe direction.
  • Timing equalization in VerifyPassword for both unknown-user and passwordless-user cases, using a real Argon2 run against dummyHash.
  • Argon2id at m=64 MiB, t=3, p=2 with bounds-checked PHC parsing (password.go:94–101) that rejects absurd parameters from a tampered hash string.
  • TOTP replay protection via a strictly-increasing time-step counter, monotonic even across re-confirmation, failing closed if the counter can't be persisted.
  • Purpose-scoped tokens. A magic-link token can't be redeemed as a password reset, and CompleteTwoFactor burns the token before checking the user ID so a mismatch can't be retried.
  • Deferred user creation for magic links, so requesting links for arbitrary addresses can't flood the user table.
  • Session revocation on first email verification when the account already had a password — the pre-registration hijack case, handled correctly and documented.
  • CI runs go vet, -race, and govulncheck. Better than most libraries at this stage.

A1 Critical sulis.go:71
sulis.go:160
magiclink.go:87
twofactor.go:57

No session-issuing path knows whether the user has a second factor

WhatThere are exactly four createSession call sites: Register, issueSessionForUser (behind Login and IssueSession), RedeemMagicLink, and CompleteTwoFactor. None consults any notion of enrolled second factors. Login returns a fully-privileged session on a correct password alone, and the 2FA flow is opt-in prose: the app is expected to stop calling Login and instead call VerifyPassword → check its own 2FA flag → CreateTwoFactorToken → CompleteTwoFactor.

Worse, RedeemMagicLink issues a session unconditionally, with no equivalent escape hatch. A magic link is therefore a permanent 2FA bypass for anyone who can read the mailbox — exactly the attacker 2FA exists to stop. There is no hook that would let an application close this even if it wanted to.

The failure mode is the dangerous kind: an app that ships password login first and adds 2FA later keeps working, keeps passing tests, and silently doesn't enforce the second factor on either the password path (if the developer forgets to switch call sites) or the magic-link path (always).

FixAdd a SecondFactorChecker interface (HasSecondFactor(ctx, userID) (bool, error)) to Config, and make the session-issuing entry points return a result type rather than a session: LoginResult{Session *Session, PendingToken string, NeedsSecondFactor bool}. Consult the checker inside Login, RedeemMagicLink, and IssueSession; when it reports a factor, mint the pending 2FA token instead of a session. Fail closed on checker errors. Make the checker a required constructor argument (not an option) so the safe path is the only path, and let applications pass an explicit NoSecondFactors{} if they genuinely have none.

A2 High passkey/passkey.go:56–71
passkey/passkey.go:144
go-webauthn login.go:354
go-webauthn registration.go:149

WebAuthn user verification is never enforced

WhatNewService builds webauthn.Config with only RPDisplayName, RPID, and RPOrigins. AuthenticatorSelection is left at its zero value, so UserVerification is the empty string, and no With* option is passed to BeginRegistration or BeginLogin. In go-webauthn v0.17.4, both ceremonies gate the check on shouldVerifyUser := session.UserVerification == protocol.VerificationRequired. Empty is not required, so the UV flag in the authenticator data is never checked.

The practical effect: an assertion produced with user presence only — a tap, no PIN, no biometric — is accepted. For passwordless passkey login that reduces the credential to a single possession factor, which is roughly the security of an unlocked bearer token on the device. For passkey-as-second-factor it removes the property that makes the second factor meaningful.

FixAdd a WithUserVerification(protocol.UserVerificationRequirement) option defaulting to required, set it on webauthn.Config.AuthenticatorSelection, and pass the matching webauthn.WithUserVerification(...) to BeginLogin and BeginDiscoverableLogin. Document that discouraged is only defensible when the passkey is a second factor behind a verified password. Add a test that a UV-absent assertion is rejected under the default.

A3 High sulis.go:223–247
emailverification.go:56–75
user.go:28

Whole-row UpdateUser invites lost updates and password-hash resurrection

WhatBoth setPassword (sulis.go:231) and stampEmailVerified (emailverification.go:65) perform read-modify-write of the entire User struct through a single UpdateUser(ctx, *User) method. Every consumer will implement that as UPDATE users SET email=?, password_hash=?, email_verified_at=?, updated_at=? WHERE id=? — the obvious reading of the interface.

Interleave ResetPassword with VerifyEmail and the second write wins with stale data. If VerifyEmail loaded the user before the reset landed, its write carries the old PasswordHash and restores it — silently undoing a password reset and re-enabling a password the user just rotated away from, which is precisely the credential an attacker would have. The mirror case also exists: a password change can clear a freshly-stamped EmailVerifiedAt.

This is a contract-level problem rather than a store bug: the interface makes the unsafe implementation the natural one, and the race window is a full store round-trip plus an Argon2 hash.

FixNarrow the interface so each mutation writes only its own column: SetPasswordHash(ctx, userID, hash string) error and SetEmailVerifiedAt(ctx, userID string, at time.Time) error, replacing the general UpdateUser for internal use. If you keep a general update, add optimistic concurrency — a Version uint64 or UpdatedAt precondition on the WHERE clause, returning a new ErrConcurrentUpdate the library retries once. Add a -race test that runs ResetPassword and VerifyEmail concurrently and asserts the new hash survives.

A4 Medium passkey/passkey.go:97–101
passkey/passkey.go:173–177
passkey/store.go:37–41

WebAuthn challenges are not atomically consumed

WhatEvery ceremony does GetChallenge followed by defer DeleteChallenge. Two concurrent FinishLogin requests carrying the same assertion both read the still-present challenge, both verify successfully, and both return a credential. The challenge is single-use in intent but not in mechanism.

This is notably inconsistent with the rest of the library, where TokenStore.ConsumeToken and recovery.Store.ConsumeCode both carry an explicit atomicity requirement in their doc comments. The passkey package is the one place a replay window was left open.

FixReplace GetChallenge/DeleteChallenge with ConsumeChallenge(ctx, key) ([]byte, error), documented as an atomic fetch-and-delete (Redis GETDEL, or DELETE ... RETURNING) returning ErrChallengeExpired when absent. Also scope login challenges per ceremony rather than per user, as BeginDiscoverableLogin already does with its ceremony ID — today a second login attempt clobbers the first device's pending challenge.

A5 Medium passkey/passkey.go:75–91

BeginRegistration never populates excludeCredentials

WhatBeginLogin loads the user's credentials from the store before starting the ceremony (passkey.go:135). BeginRegistration does not — it passes the caller's *User straight through, so excludeCredentials is whatever the caller happened to put in User.Credentials, which nothing in the API says they must populate. Given that the sibling method does it for you, callers will reasonably assume this one does too.

The result is that the same authenticator can be registered repeatedly, producing duplicate credentials for one device. That's mostly a hygiene and user-confusion problem, but it also defeats the browser's built-in “you already registered this key” prompt, which is the signal a user would otherwise get if they were being socially engineered into enrolling an attacker-controlled credential during a session they didn't initiate.

FixLoad credentials from the store inside BeginRegistration, exactly as BeginLogin does, and ignore whatever the caller passed in User.Credentials. Consider dropping that field from the exported struct so it can't be misread as an input.

A6 Medium passkey/passkey.go:56–71
passkey/passkey.go:198–212

Discoverable login is offered but resident keys are never requested

WhatBeginDiscoverableLogin / FinishDiscoverableLogin implement usernameless login, but registration never asks the authenticator for a discoverable (resident) credential — AuthenticatorSelection.ResidentKey and RequireResidentKey are both unset. Whether a credential ends up discoverable is then entirely up to the authenticator's default.

Security-relevant because of the fallback: when usernameless login finds nothing, users are pushed back to the password path, and an unreliable passkey flow trains people to reach for the weaker credential. It also makes the feature's behavior platform-dependent in a way that's hard to debug.

FixAdd a WithResidentKey(protocol.ResidentKeyRequirement) option, default it to required when the service is configured for discoverable login, and set both ResidentKey and the legacy RequireResidentKey for older-authenticator compatibility. Persist whether the resulting credential is actually discoverable so the app can tell the user.

A7 Medium passkey/passkey.go:95, 164, 221
go-webauthn protocol/decoder.go:10–22

Unbounded request body handed to WebAuthn JSON parsing

WhatFinishRegistration, FinishLogin, and FinishDiscoverableLogin take an *http.Request and pass it directly to go-webauthn. Its decodeBody is a bare json.NewDecoder(body).Decode(v) with no size limit at all. Since the response struct holds base64 string fields, a large body means a proportionally large allocation per request, on an unauthenticated endpoint in the passwordless case.

Modest on its own, but it's free to fix and the library is the right place: because sulis owns the *http.Request in its signature, consumers have no natural hook to wrap it.

FixBefore parsing, replace the body with http.MaxBytesReader(nil, r.Body, maxCeremonyBody) — 64 KiB is generous for a WebAuthn response with attestation. Make it a configurable option. Better still, add transport-agnostic variants (FinishLoginWithResponse([]byte)) so the package doesn't require net/http at all, and the HTTP wrappers become thin.

A8 Medium totp/totp.go:160–182
totp/store.go:20–27

totp.Enroll silently destroys a working enrollment

WhatEnroll generates a fresh secret with a new credential ID and calls SaveTOTP, which is keyed by user for retrieval. There is no check for an existing verified credential, and the store contract explicitly blesses this (“Re-enrollment is unaffected: Enroll always generates a new credential ID”). So one call — a double-submitted setup form, a CSRF'd POST to an enrollment endpoint, a retried request — replaces a confirmed second factor with an unconfirmed one.

Depending on how the application models “this user has 2FA,” the outcome is either lockout (Validate now returns ErrTOTPNotVerified) or a genuine downgrade (the app's gate reads the credential's Verified flag and concludes 2FA is off). Neither should be reachable without the user re-authenticating.

FixReturn a new ErrTOTPAlreadyEnrolled when a verified credential exists, unless the caller passes an explicit re-enroll intent (ReplaceEnrollment(ctx, userID, ...)). Keep the pending enrollment in a separate slot from the active one so a half-finished setup can never take the live factor offline, and document that enrollment endpoints require step-up authentication (see C7).

Group BUnsafe defaults and API footguns

The code here is correct. The problem is that the easy call is the unsafe one — which matters more, not less, once other people are the ones calling it.

B1 High config.go:38
config.go:118–123
sulis.go:405–413

Rate limiting is off by default and fails open

WhatLimiter defaults to nil, and allow treats nil as a no-op. The README calls rate limiting “required in production,” but nothing enforces that, and the failure is invisible: password guessing, reset flooding, and TOTP brute force all just work at full speed. A default that documentation has to apologize for is the wrong default.

Two further gaps. There's no IP dimension — keys are "password:"+email, so an attacker spreading guesses across many accounts from one host is never throttled, and conversely one abusive host can lock out a targeted user by burning their email's budget. And totp.WithLimiter is a separate wiring step, so it's independently forgettable.

FixShip a working in-memory token-bucket limiter and make it the default; require an explicit WithoutRateLimiting() to disable, so opting out is a visible line of code. Let the auth methods accept optional caller context (client IP) and limit on both dimensions, with per-account and per-IP budgets tuned separately. Ship a Redis reference implementation for multi-instance deployments, and note in the docs that the in-memory default is per-process.

B2 Medium sulis.go:252–268

CreatePasswordResetToken is a user-enumeration oracle

WhatIt returns ErrUserNotFound verbatim for an unregistered address. The README correctly tells consumers to flatten that in their handler, but the library is handing them a loaded gun and a warning label — and every consumer must get it right independently, forever. There's also a timing side channel that no amount of response normalization fixes: the existing-user path does a token generation plus a store write, the missing-user path returns immediately.

By contrast CreateMagicLinkToken has no such oracle, because it defers user creation to redemption. The two sibling flows disagree on their threat model.

FixMake the safe behavior the default: return ("", nil) for an unknown address so there is nothing for a handler to leak, and generate-then-discard a token on that path to equalize timing. If a caller genuinely needs to distinguish the cases (an admin tool), expose that as a separate explicitly-named method. Also consider an option for Register to defer the “address already taken” answer to email rather than returning ErrUserAlreadyExists synchronously.

B3 Medium sulis.go:315–317

RevokeSession takes no user ID, so ownership is never checked

WhatRevokeSession(ctx, sessionID) deletes whatever session ID it's given. A “sign out this device” endpoint that passes a session ID from the request — the obvious implementation — lets any authenticated user revoke any other user's sessions. That's a textbook IDOR, and the API shape actively invites it.

FixChange the signature to RevokeSession(ctx, userID, sessionID string) error and have the store scope the delete to both, returning ErrSessionNotFound on a mismatch. The extra argument makes the ownership check unskippable rather than merely documented.

B4 Medium totp/totp.go:216–244

totp.Validate returns (bool, error), and the wrong-code case returns (false, nil)

WhatAn invalid code is not an error — it's false with a nil error. So the idiomatic-looking Go below is a complete 2FA bypass, and it reads as correct in review:

if _, err := totpSvc.Validate(ctx, userID, code); err != nil {
    return unauthorized(w)
}
// ← reached for *every* wrong code
grantSession(w, userID)

Every other authentication primitive in this library signals failure with an error (ErrInvalidCredentials, ErrTokenInvalid, ErrCodeInvalid). This one is the exception, in the place where a mistake is least recoverable.

FixReturn only error: nil means valid, ErrTOTPInvalid means it isn't. This matches recovery.Consume and makes the bypass unwritable. It's a breaking change, which is free right now and expensive after v1.

B5 Low session.go:16
sulis.go:341–346

Session.Token exists on the struct the store receives

WhatcreateSession carefully copies the session and blanks Token before calling CreateSession. The discipline is correct but it lives in one function rather than in the type: the field is present on the struct a store implementation is handed, so an INSERT written from the struct's shape, or any future call site that forgets the copy, persists a raw bearer token.

FixRemove Token from Session and return the raw token as a separate value — createSession(...) (*Session, string, error), surfaced as e.g. LoginResult.SessionToken. Then no store can persist it, because no store is ever given it.

B6 Low sulis.go:138–151

IssueSession is unauthenticated session minting behind a doc comment

WhatThe comment says callers “MUST invoke this only after fully authenticating the user.” That's the only thing standing between a user ID and a valid session. It's a necessary primitive for passkey and 2FA completion, but as a bare exported method taking a string it's the single most misusable call in the package.

FixMake the type system carry the requirement: have it take an unexported-field Authentication value that only the completion paths (CompleteTwoFactor, a new CompletePasskeyLogin) can construct. Applications integrating a factor sulis doesn't know about get an explicitly-named escape hatch — IssueSessionUnchecked — whose name shows up in their code review, not just in your docs.

Group CMissing for the advertised feature set

Gaps rather than bugs: things a library promising “passwords, magic links, 2FA, and passkeys” needs before others depend on it.

C1 High user.go:9–20
emailverification.go:56

No ChangeEmail — so email changes don't reset verification

WhatNothing in the library clears EmailVerifiedAt when the address changes, and there's no method that owns the change. Applications will mutate user.Email and call UpdateUser directly, keeping the old verified timestamp. The result is an unverified address that the library treats as verified, which defeats the entire RequireVerifiedEmail gate you just shipped — and it's also the standard account-takeover pivot, since password reset then delivers to the new address.

The email-verification token is correctly bound to the address it was issued for, which shows the threat was considered; the write path just isn't owned by the library.

FixAdd ChangeEmail(ctx, userID, newEmail string) (token string, err error): normalize and uniqueness-check the address, store it as pending rather than live, issue a verification token bound to it, and only swap the live address (clearing and re-stamping EmailVerifiedAt) on redemption. Revoke sessions and purge outstanding reset tokens on the swap, and return enough information for the app to notify the old address — that notification is what lets a victim catch a takeover in progress.

C2 Medium sulis.go:213–221

Password policy is length-only — no breach or blocklist check

WhatcheckPasswordPolicy checks 8–1024 bytes and nothing else. NIST SP 800-63B explicitly expects verifiers to compare prospective secrets against a list of known-compromised values; that check does far more for real-world resistance than any composition rule. password123 currently passes.

FixAdd a PasswordChecker interface (Check(ctx, password string) error) consulted by Register, ChangePassword, SetInitialPassword, and ResetPassword, with a new ErrPasswordCompromised. Ship two implementations: a small embedded blocklist of the most common passwords, and an HIBP k-anonymity client (5-character SHA-1 prefix, so the password never leaves the process) with a fail-open-or-closed switch. Raise the default minimum to 12 while you're breaking the API. Also apply Unicode NFKC normalization before hashing so a password typed on a different keyboard still verifies.

C3 Medium password.go:42–58
sulis.go:127–135

No rehash-on-login, so Argon2 parameters can never be raised

WhatverifyPassword reads the cost parameters out of the stored PHC string and verifies against those. It never compares them to the configured ones. Raise Argon2Params in five years and every existing user keeps their original cost forever — the config change is silently cosmetic for your entire installed base.

FixAdd needsRehash(encoded string, want Argon2Params) bool and, on a successful VerifyPassword, transparently re-hash with the current parameters and write it back via the narrow SetPasswordHash from A3. Log it through the event sink (C9) so operators can watch the migration drain. This is also the mechanism that lets you adopt a future algorithm without a forced reset.

C4 Medium totp/totp.go:166–181
totp/store.go:9–16

TOTP secrets are plaintext in the store, and passwords have no pepper option

WhatCredential.Secret is handed to the store as base32 plaintext. The README pushes encryption-at-rest entirely onto the consumer, which means it will frequently not happen — and a database leak then yields every enrolled user's shared secret, usable to mint valid codes indefinitely and silently. Unlike a password hash, there is no work factor buying you time.

Related: password hashes have no application-held pepper. A pepper doesn't help against a full application compromise, but it makes a database-only leak entirely uncrackable, which is the far more common breach shape.

FixAdd an Encryptor interface (Encrypt/Decrypt([]byte) ([]byte, error)) with an AES-256-GCM implementation keyed from a caller-supplied secret, and encrypt Credential.Secret inside the totp package so stores only ever see ciphertext. Include a key-ID prefix so keys can be rotated. Separately, add WithPepper([]byte) that HMAC-SHA256s the password with the pepper before Argon2, documented as unrecoverable-if-lost.

C5 Medium user.go:9–20
sulis.go:293–312

No account lockout or disable, and ValidateSession checks nothing but expiry

WhatUser has no DisabledAt or LockedUntil, and ValidateSession only checks the clock. There is no way to take an account out of service: you can delete its sessions, but the next correct password mints a new one. For a compromised or abusive account, the only tool is deleting the user.

Rate limiting (B1) throttles guessing but never stops it, and it can't respond to a credential-stuffing signal by parking the account until the owner is contacted.

FixAdd DisabledAt *time.Time and LockedUntil *time.Time to User, check both in VerifyPassword, every session-issuing path, and ValidateSession (so existing sessions die immediately), with ErrAccountDisabled / ErrAccountLocked. Add DisableUser/EnableUser, and an optional automatic lockout after N consecutive failures with exponential backoff — carefully, since attacker-triggered lockout is itself a denial of service; prefer a long backoff over a hard lock.

C6 Medium middleware.go:21–39
middleware.go:53–67

Cookie middleware ships without cookie or CSRF helpers

WhatAuthenticate reads a cookie named session, but the library never sets that cookie and offers no CSRF defense — the README correctly identifies both as the consumer's problem. That leaves every adopter to independently get HttpOnly, Secure, SameSite, Path, and a CSRF strategy right, on the one code path where a mistake is remotely exploitable by any website the user visits.

The mixed-mode extraction adds a subtlety: because a Bearer header is accepted on the same handlers, a CSRF defense predicated on “we only accept cookies here” doesn't hold, and vice versa.

FixShip SessionCookie(token string, expires time.Time) *http.Cookie and ClearSessionCookie() with correct defaults (HttpOnly, Secure, SameSite=Lax, Path=/, __Host- prefixed name). Add a RequireSameOrigin middleware that rejects state-changing requests failing a Sec-Fetch-Site/Origin check, plus a double-submit CSRF token helper for older clients. Make the cookie name configurable, and add WithTokenSource(CookieOnly|BearerOnly|Both) so an app can close the path it isn't using.

C7 Medium — (absent)

No step-up (re-authentication) primitive for sensitive operations

WhatEnrolling TOTP, adding or deleting a passkey, disabling 2FA, changing email, and regenerating recovery codes are all operations that should require proving you're still the account owner right now — not merely holding a session cookie from this morning. The library has no notion of “recently authenticated,” so applications either skip the check or invent their own.

This is what makes A8 (enrollment destroying a verified factor) reachable from a single request, and it's the standard mitigation for session-hijack-to-persistent-takeover.

FixRecord AuthenticatedAt (and ideally the method used) on Session, add RequireRecentAuth(ctx, session, maxAge time.Duration) error returning ErrReauthRequired, and a ReAuthenticate flow that re-verifies a password or passkey and refreshes the stamp without minting a new session.

C8 Medium config.go:28
magiclink.go:16–35

Magic links share a 1-hour TTL with password resets and aren't bound to a browser

WhatOne TokenDuration governs both flows, so a magic link — which is a full credential, delivered in cleartext through email, and often forwarded, logged by mail scanners, or previewed by link-expanding clients — lives as long as a password reset. Nothing ties redemption to the browser that requested it, so anyone who obtains the URL within the window is signed in.

FixSplit the knob: WithMagicLinkDuration at 10–15 minutes, keep resets at an hour. Then bind the link to its requester: return a second opaque nonce from CreateMagicLinkToken for the app to set as a short-lived HttpOnly cookie, store its hash alongside the token, and require it at redemption — a leaked or forwarded link is then useless on any other browser. Make the binding optional (some users legitimately open mail on another device) but default it on, and consider requiring an explicit confirmation click at redemption so mail-scanner prefetches can't consume the token.

C9 Low — (absent)

No security event hook

WhatThere is no way to observe failed logins, rate-limit trips, 2FA enrollment changes, recovery-code use, password resets, or new-device sign-ins. Applications can infer some of it from returned errors, but not consistently, and the interesting events (a recovery code used, a factor removed) are exactly the ones a user should be emailed about.

FixAdd an EventSink interface with a typed event struct (kind, user ID, timestamp, outcome, caller-supplied request context) and emit from every decision point. Guarantee in the docs that no raw secret ever appears in an event — the codebase already holds that line for error messages. A no-op default keeps it zero-cost, and a slog adapter makes it one line to wire.

C10 Low session.go:24–30
sulis.go:325–349

Users can't see or manage their own sessions

WhatSessionStore has no list operation, so there's no way to build a “where you're signed in” screen — the control that lets a user notice and evict an intruder themselves. Session.Metadata exists but nothing populates it, so even if you listed sessions you'd have no IP, user agent, or location to show. Sessions also have a single fixed 24-hour expiry with no idle-timeout or sliding-renewal option.

FixAdd ListUserSessions(ctx, userID) ([]Session, error), let session creation accept caller-supplied metadata (IP, user agent, a device label), and record LastSeenAt on validation. Add an idle timeout alongside the absolute lifetime, plus RefreshSession that rotates the token while preserving the session row.

C11 Low recovery/recovery.go:91–107

Recovery codes aren't wired into the 2FA lifecycle

WhatThe primitives are sound — 80 bits of entropy, hash-only storage, atomic single-use consumption. What's missing is the surrounding lifecycle: consuming a code doesn't revoke other sessions or signal that the user should re-enroll their factor, disabling TOTP doesn't purge the codes, and nothing warns when the set is nearly exhausted. Consume also has no limiter, which is defensible at 80 bits but inconsistent with the rest of the library and forfeits the attack telemetry.

FixHave Consume report remaining count so callers can prompt regeneration, add a limiter for consistency and telemetry, and document the expected sequence: a consumed code should revoke other sessions, emit an event, and push the user toward re-enrolling a real factor. Purge codes when the last second factor is removed.

C12 Low passkey/store.go:9–27

Passkey credentials lack the metadata users and policies need

WhatCredential records the ID, public key, attestation type, AAGUID, and sign count — but not BackupEligible/BackupState (is this passkey synced to a cloud account, or bound to this hardware?), transports, a user-assigned name, or LastUsedAt. Synced-versus-hardware-bound is a real policy input for anyone with a stricter bar, and it's discarded at registration. There's also no guard against deleting the last credential of a passwordless account, which is a straight path to permanent lockout.

FixPersist the backup flags, transports, and attachment from the registration response; add Name and LastUsedAt so a management UI is buildable; add DeleteCredentialsByUserID; and make credential deletion refuse to remove the last usable factor unless the caller passes an explicit override.

Group DProject and supply chain

Open-sourcing changes the threat model: strangers will trust this, hand-write the stores it depends on, and need a way to report what they find.

D1 Low — (absent)

Ship tested reference stores and a conformance suite

WhatThis is the highest-leverage item in Group D, and arguably in the whole document after A1. The store interfaces are the security boundary, and several carry requirements that are invisible in the type system: ConsumeToken must be atomic, SaveTOTP must reject counter regressions, ConsumeCode must be atomic, and (per A3) user updates must not clobber concurrent writes. Right now all of that is prose in doc comments, and every adopter writes the SQL themselves. Most will get at least one of them subtly wrong, and no test they write will tell them.

FixAdd a sqlstore subpackage with audited Postgres and SQLite implementations of every interface, including the required indexes and uniqueness constraints. Then add a storetest package exporting a conformance suite — storetest.RunUserStore(t, factory) and friends — that hammers the atomicity requirements with concurrent goroutines under -race, so a consumer can prove their own store is correct in five lines. Publish that suite as part of the documented integration path, not as an internal test helper.

D2 Low .github/workflows/ci.yml:14

Tighten CI: unpinned tool, and no static analysis beyond go vet

Whatgo run golang.org/x/vuln/cmd/govulncheck@latest resolves and executes whatever @latest means on the day CI runs — an unpinned dependency with code execution in your pipeline. Beyond that, go vet is the only analysis, and the workflow declares no permissions block, so it inherits the repository default token scope.

RoadmapWhat to do, in order

Ordered by risk retired per unit of work. Phases 1 and 2 are the ones that change the library's actual security properties; the rest is depth and polish.

Close the bypasses Phase 1 · A1, A2, A3

The three findings that undermine advertised guarantees. Nothing else matters as much.

  • Add SecondFactorChecker and make Login, RedeemMagicLink, and IssueSession return a result type that can demand a second factor. Close the magic-link bypass explicitly, with a test.
  • Require WebAuthn user verification by default and thread the requirement through registration and both login ceremonies.
  • Replace whole-row UpdateUser with column-scoped writes, and add the concurrent reset-versus-verify regression test.

Make the defaults safe Phase 2 · B1–B5, A4, A7, A8

Everything here is a case where the correct behavior currently depends on the adopter reading the README.

  • Rate limiting on by default with a shipped in-memory limiter; per-IP and per-account dimensions.
  • ConsumeChallenge for atomic single-use WebAuthn challenges; per-ceremony keys.
  • totp.Validate returns error only; Enroll refuses to clobber a verified factor.
  • RevokeSession takes a user ID; CreatePasswordResetToken stops leaking existence; Session.Token leaves the struct.
  • Bound the WebAuthn request body.

Own the store boundary Phase 3 · D1, D3, D4

The security properties are only as good as the SQL other people write. Stop delegating that to prose.

  • sqlstore for Postgres and SQLite, with schema and indexes.
  • storetest conformance suite that proves atomicity under -race, published as the supported integration path.
  • Bring passkey coverage up with a test authenticator; add fuzz targets and concurrency tests.

Complete the feature set Phase 4 · C1–C12

The flows an adopter will otherwise build themselves, less carefully.

  • ChangeEmail with pending-address verification, session revocation, and old-address notification.
  • Step-up authentication; account disable and lockout; session listing with device metadata.
  • Breach checking and rehash-on-login; TOTP secret encryption and an optional password pepper.
  • Cookie and CSRF helpers; split magic-link TTL with browser binding; event sink.

Prepare for strangers Phase 5 · D2, D5, D6, D7

Do this before the repository goes public, not after the first issue arrives.

  • SECURITY.md with a real reporting path; an explicit threat model.
  • Package docs and runnable examples; CONTRIBUTING.md; CHANGELOG.md.
  • Hardened CI: pinned tools and actions, scoped permissions, static analysis, coverage floor.
  • Land all breaking changes in one pass, then tag v1.

Worth considering beyond this list

  • An external cryptographic review once Phases 1–3 land — the value of a second pair of eyes on an auth library scales with the number of people who'll depend on it.
  • A documented decision on what this library deliberately won't do (OAuth/OIDC provider, SAML, SCIM, sessions in JWTs), so scope creep has something to push against.
  • An integration example application, wired end-to-end, that doubles as a smoke test for the ergonomics of the post-Phase-2 API.
